# CASETRACE Agent Tools

Phase 2.5 adds a diagnostic-document discovery check to the contradiction role.
Original diagnostic documents or structured cardiology/actionable reports trigger
the existing bounded document/encounter/referral retrieval, shared with Phase 2.4.
At most twenty originals, three working-label comparisons and twenty comparison
anchors are considered within existing role/global budgets. No new permissions,
clinical endpoint or diagnosis tool is introduced. Narrative working assessments
retain explicit certainty or unknown certainty; generic notes remain nonspecific
context. Symptom correlation is required for a positive reconsideration question.
Independent search and complete source reconstruction precede publishing a typed
comparison and its source-linked Hypothesis. The hypothesis remains clinically
inconclusive. Incidental, supportive, inconclusive, conflicting or wrong-context
results cannot become a positive challenge. No diagnosis, probability, treatment
instruction or allegation of improper care is generated by this workflow.

Phase 2.4 extends the existing contradiction role's referral check into a result
workflow investigation. It lists diagnostic reports, discovers finalized
actionable results, searches the unfiltered document catalog and retrieves at
most twenty originals with version/hash checks, plus encounters and referrals.
The existing thirty-call role/global budgets and permissions still apply.
The typed result_workflow envelope records all searched source fingerprints,
search completeness, eleven lifecycle stages and source-native timestamps.
Appointments are covered only through referral fields; no appointment tool is
invented. Truncation or unavailable independent search leaves absence claims
unresolved. Later completion and communication evidence remain in the lifecycle.
The verifier repeats the unfiltered clinical search and resolves every original;
administrative closure never verifies completed care or patient notification.

Phase 2.3 MedicationAgent additionally searches documents by up to four explicit
ingredients and the bounded medication/dose/hold/restart query set. It retrieves
original versions/hashes, retains at most twenty documents, and proposes at most
six reconciliation relationships before lower-priority observations. Its existing
thirty-call allowance and permissions remain unchanged. Missing ingredient or
formulation identity remains uncertain. Laboratory evidence is handed off from
the laboratory specialist's existing results by the orchestrator; the medication
role has no new laboratory permission. The bounded
`specialist.evidence_requested` event identifies providing/requesting roles and
source references, without clinical prose. See
[Phase 2.3 report](evaluation/phase2-03-medication-investigator-report.md).

Phase 2.2 relationship assembly consumes the existing provenance-bearing original
tool records. It adds no tool or permission. Constituent assertions preserve
source IDs/version/hash/encounter and named times; independent verification
resolves originals through the existing SourceResolver boundary. Search hits do
not supply factual assertions. See
[relationship architecture](architecture/clinical-relationship-reasoning.md).

Refactor 05 adaptive specialists use the same registry, role allowlists and
input/result contracts. Follow-up approval validates returned source versions,
patient scope and document/encounter associations before scheduling. Global and
per-role budgets span all tasks. Search hits become original version/hash-checked
documents before reassessment. No tool or permission is added. See
[executable runtime architecture](multi-agent-architecture.md).

Phase 3 implementation uses `app/tools/registry.py` as the executable registry.
It exposes typed schemas, descriptions and explicit role scopes, checks the
persisted agent/run identity, enforces patient scope and budgets and records
failed validation/permission calls. Synthesis has no clinical tools. The optional
get_referrals read is restricted to contradiction investigation for follow-up
reconciliation. get_imaging_asset_metadata resolves registered metadata with
patient ownership checked through the parent study; its version tracks that study.
No image interpretation tool is introduced. Search returns explicitly marked
snippets; document detail is separately retrieved and asset-integrity checked.
Refactor 04 adds tool-specific inputs and targeted filters over ClinicalSource.
build_patient_timeline defaults to clinical events for existing specialists and
accepts explicit authorized categories for aggregation. Original records remain
in records; a separate timeline projection preserves named times and precision.
The supervisor's existing report projection remains unchanged.

## Refactor 04 executable contract

See [inventory, coverage and measured outcomes](refactoring/08-clinical-tools-refactor-report.md).
The following supersedes illustrative input/output examples where they differ:

- `app/tools/inputs.py` defines each tool's Pydantic schema. Registry catalog
  exposes it alongside operation-specific descriptions and scope. Unknown fields,
  malformed IDs, unsupported enum values, naive/reversed time ranges, invalid
  paging and conflicting selectors fail. Page defaults remain limit=20/offset=0;
  limits are 1–100, offset 0–10000. Instants require offsets; bounds are inclusive.
- All calls are scoped to the investigation's selected patient. Registry supplies
  patient_id when omitted. search_patient matches only this patient's ID, MRN or
  display name, case-insensitively; it is not cross-patient discovery.
- Exact calls accept record_id or the documented encounter_id/document_id/
  observation_id/medication_id/report_id/imaging_asset_id/imaging_study_id alias.
  Supplying both forms is rejected. An optional encounter_id association is
  checked on detail calls except get_encounter (where it is the selector).
  Optional source_version/source_hash reject stale references. Imaging-report
  preconditions refer to the returned report document, not the parent study.
- Encounter filters use started_at, observations specimen_collected_at, document
  search event_at, medication history ordered_at, reports issued_at, imaging
  performed_at and referrals ordered_at. Stable clinical ordering is ascending
  with source-ID ties and unknowns last; search uses stable document-ID order.
  Date-only medication start/end remain original values and do not become order
  times. Original hospital HTTP sorting/filter semantics are retained.
- Analyte and medication names and body_region use exact case-insensitive equality;
  test codes, departments, IDs and other enums use exact equality. Search matches
  a case-insensitive substring in title or clinical text, including whitespace
  literally. Empty query lists document metadata. Both clinical-note tool names
  remain document aliases; document_type explicitly narrows retrieval.
- Search SourceRecord uses representation=search_hit and representation_hash over
  the returned hit data. source_hash/source_version continue identifying the
  original hospital DTO. representation=source is the default for original DTOs.
  Never use a snippet's fields with an original-source hash as an evidence anchor.
  Full retrieval and deterministic verification are still required.
- compare_lab_results accepts a distinct record_id/other_id pair OR test_name
  and/or test_code. Analyte selection checks the whole selected series and returns
  its chronologically earliest/latest pair. Both coded tests must have equal
  codes; when both codes are absent only exact case-insensitive names match.
  Mixed coded/uncoded observations, incompatible/missing units, nonnumeric values,
  invalid timestamps and missing collection times fail. No conversions occur.
  Original values/times remain in records. Optional analysis returns direction,
  signed change_absolute and change_percent (null for zero baseline), without
  clinical interpretation. Insufficient observations are an explicit error.
- Timeline include supports the five documented categories (encounters, events,
  observations, medications, documents) for the timeline role. That role explicitly
  gains medication-history read access; the other role permissions are unchanged.
  Each category needs its underlying read permission. Catalog allowed_categories
  reflects this. Imaging/report/referral and diagnosis/symptom categories are
  rejected for this role, even though the aggregation implementation can project
  those DTOs. New scopes require a deliberate authorization change.
  Date-only entries form a separate labelled group after instants; unknowns last.
  No ordering of a date-only entry relative to same-day instants is asserted.
  Timeline date filters apply to the named primary time and exclude unknown/dates.
  Aggregation and analyte selection are capped at 10000 scanned records.
- ToolResult retains status, records, source_refs, total, has_more, retrieved_at;
  optional analysis and timeline are additive internal fields. Errors remain
  propagated HospitalError/Pydantic validation/timeout exceptions with durable
  failed audit events. An empty valid search is status=empty, not a missing-patient
  or missing-record substitute. partial means another page exists.
- Registry validates typed source DTOs, patient ownership, identity, content hash,
  versions, unique references, result size and pagination. Asset ownership is
  resolved through its parent study. No filesystem paths or raw file capability
  enter tool results. Documents retain MIME, has_asset, clinical text and original
  source identity/version/hash; binary integrity is checked through AssetReader.
- Audit preserves actual start/end/status/duration and source IDs. Sanitized IDs
  and pagination plus a fingerprint of allowlisted arguments permit correlation
  without logging query text or complete documents. Actor/run validation and
  separate short commits remain authoritative; failed validation, authorization,
  timeout, budget and output checks cannot produce a successful completion.

No public endpoint, source fingerprint, migration, provider or specialist reasoning
rule changes in this milestone. No cache, semantic search or pixel analysis is added.

SQLite migration preserves all tool names, scopes, schemas, provenance and audit behavior. Follow [development stack](development-stack.md): commit audit start before external work, close repository read sessions promptly, and commit results separately through the controlled persistence service. Agents never own database sessions.

**Status:** Canonical  
**Purpose:** Define the tool interface through which CASETRACE agents retrieve, inspect, compare, and verify clinical evidence.

---

# 1. Purpose

CASETRACE agents must never directly access the database.

Agents interact with the simulated clinical information system exclusively through registered tools.

```text
Agent
  ↓
Tool Registry
  ↓
Tool Permission Check
  ↓
Tool Handler
  ↓
ClinicalRecordService
  ↓
Simulated Hospital
  ↓
SQLite
```

The tool layer is the security, abstraction, provenance, and observability boundary between agents and clinical data.

---

# 2. Core Principle

The agent should behave like an investigator using a hospital information system.

It should not behave like an application querying its own database.

Correct:

```text
Timeline Agent
  ↓
get_encounters(patient_id)
  ↓
search_clinical_notes(...)
  ↓
get_clinical_note(document_id)
  ↓
compare_lab_results(...)
```

Incorrect:

```text
Timeline Agent
  ↓
SQL query
  ↓
patients + notes + labs + medications
```

Agents must use tools even when direct database access would be easier.

---

# 3. Tool Design Goals

Every tool must provide:

1. A narrow purpose
2. Explicit input schema
3. Explicit output schema
4. Permission scope
5. Validation
6. Audit logging
7. Source provenance
8. Deterministic behavior
9. Stable identifiers
10. Clear error states

Tools should expose **clinical capabilities**, not database implementation details.

---

# 4. Tool Registry

All tools are registered through a central registry.

```python
class ToolRegistry:
    def register(tool: AgentTool) -> None:
        ...

    def get(name: str) -> AgentTool:
        ...

    def list_for_agent(agent_name: str) -> list[AgentTool]:
        ...

    def execute(
        tool_name: str,
        arguments: dict,
        context: ToolContext,
    ) -> ToolResult:
        ...
```

Recommended location:

```text
apps/api/app/tools/
  registry.py
  base.py
  schemas.py

  patient_tools.py
  encounter_tools.py
  laboratory_tools.py
  medication_tools.py
  document_tools.py
  imaging_tools.py
```

---

# 5. Base Tool Contract

Every tool implements the same conceptual interface.

```python
class AgentTool:
    name: str
    description: str
    permission_scope: str
    input_schema: type
    output_schema: type

    async def execute(
        self,
        arguments: dict,
        context: ToolContext,
    ) -> ToolResult:
        ...
```

A tool must not:

- Access `ground_truth`
- Access evaluator state
- Generate unsupported clinical facts
- Modify clinical records unless explicitly designated as a write tool
- Bypass permission checks
- Hide source provenance

---

# 6. Tool Context

Every tool execution receives investigation context.

```python
class ToolContext:
    investigation_id: str
    agent_run_id: str
    agent_name: str
    patient_id: str
    allowed_scopes: list[str]
    correlation_id: str
```

The context is generated by the orchestration engine.

Agents must not fabricate:

```text
investigation_id
agent_run_id
patient_id
permission scopes
```

# 7. Tool Result Contract

Every tool returns a standardized result.

```json
{
  "status": "success",
  "records": [],
  "source_refs": [],
  "metadata": {},
  "retrieved_at": "2026-01-20T12:30:00Z"
}
```

Supported statuses:

```text
success
empty
partial
error
forbidden
not_found
invalid_request
```

# 8. Source Reference

Every returned clinical record must be traceable.

```json
{
  "type": "document",
  "id": "DOC-014"
}
```

Supported source types:

```text
patient
encounter
clinical_event
observation
medication
document
diagnostic_report
imaging_study
imaging_asset
referral
```

A source reference may optionally include:

```json
{
  "type": "document",
  "id": "DOC-014",
  "title": "Specialist Consultation Note",
  "event_at": "2026-02-04T10:00:00"
}
```

---

# 9. Provenance Requirement

Tool results must preserve provenance all the way through the investigation.

```text
Clinical record
    ↓
Tool result
    ↓
Agent finding
    ↓
Evidence item
    ↓
Verification
    ↓
Final report
```

An agent must never produce:

```text
"Evidence shows..."
```

without being able to identify the underlying source.

# 21. Evidence Search Tool

## 21.1 `search_documents`

This tool is intentionally broad enough to support targeted investigation.

Agents should prefer narrow searches.

Bad:

```text
query: "everything"
```

Good:

```text
query: "first episode of dizziness"
```

Better:

```text
query: "dizziness onset January"
```

The purpose is to simulate investigator behavior:

```text
Hypothesis
   ↓
Targeted search
   ↓
Source retrieval
   ↓
Verification
```

# 24. Patient Scope

Every clinical tool must be scoped to the investigation's patient.

If the investigation is for:

```text
PAT-001
```

the agent must not retrieve:

```text
PAT-002
PAT-003
```

unless an explicit future workflow supports cross-patient comparison.

For CASETRACE v1:

> **One investigation = one patient.**

# 25. Ground Truth Protection

No tool may expose:

```text
ground_truth
investigation_target
required_discovery
acceptable_conclusions
red_herrings
expected_evidence
evaluation_metrics
```

Forbidden tool examples:

```text
get_ground_truth()

get_expected_answer()
get_case_solution()
```

These tools must not exist in runtime.

# 26. No Direct Database Access

The following imports are forbidden inside agent implementations:

```python
from sqlalchemy import ...
from sqlalchemy.orm import ...
from app.core.database import ...
```

Agents interact through:

```python
await tool_registry.execute(...)
```

or an equivalent agent-tool abstraction.

Database access belongs below the tool boundary.

# 29. Error Handling

Tools must fail explicitly.

### Not found

```json
{
  "status": "not_found",
  "error": {
    "code": "DOCUMENT_NOT_FOUND"
  }
}
```

### Invalid input

```json
{
  "status": "invalid_request",
  "error": {
    "code": "INVALID_ARGUMENT"
  }
}
```

### Internal failure

```json
{
  "status": "error",
  "error": {
    "code": "TOOL_EXECUTION_FAILED"
  }
}
```

Agents should be able to continue when an individual tool fails, where clinically appropriate.

---

# 30. Empty Results

Empty results are not necessarily errors.

Example:

```json
{
  "status": "empty",
  "records": [],
  "source_refs": []
}
```

The agent should interpret this as:

> No matching records were found.

not:

> The clinical event did not happen.

Absence of evidence is not automatically evidence of absence.

---

# 31. Partial Results

Tools may return partial results when appropriate.

```json
{
  "status": "partial",
  "records": [],
  "metadata": {
    "limit": 20,
    "returned": 20,
    "has_more": true
  }
}
```

Agents should request additional results when necessary.

---

# 32. Pagination

Search and list tools should support:

```json
{
  "limit": 20,
  "offset": 0
}
```

or cursor-based pagination.

For v1, offset pagination is acceptable.

Maximum:

```text
limit <= 100
```

to prevent uncontrolled retrieval.

---

# 33. Tool Result Size

Tools should avoid returning unnecessarily large payloads.

Search tools return:

```text
metadata
snippet
source reference
```

Retrieval tools return:

```text
complete record/document
```

This creates an intentional two-step retrieval pattern:

```text
SEARCH
  ↓
IDENTIFY SOURCE
  ↓
RETRIEVE SOURCE
```

This is important for the CASETRACE demo because viewers should be able to see agents discovering evidence rather than magically receiving everything.

---

# 34. Search Ranking

Search tools may rank results using:

```text
text relevance
event proximity
document type
timestamp
department
```

However, ranking must not hide potentially relevant records.

The tool should return enough metadata for the agent to decide what to inspect.

# 35. Deterministic vs LLM Responsibilities

### Tools should perform:

```text
Database retrieval
Filtering
Sorting

Numeric comparison
Record linking
Source identification

```

### Agents should perform:

```text
Hypothesis generation

Pattern recognition
Evidence prioritization
Contradiction interpretation
Question formulation
Investigation planning
Narrative synthesis
```

### Never ask an LLM to perform deterministic work unnecessarily.

For example:

Bad:

```text

"Calculate whether hemoglobin decreased."
```

Good:

```text

        ↓
deterministic calculation
        ↓
LLM interprets significance
```

# 36. Tool Calls and Clinical Claims

A tool call is evidence retrieval.

A tool call is not itself a clinical conclusion.

Example:

```text
get_lab_results()
```

returns:

```text
Hemoglobin = 8.9 g/dL
```

The agent may then propose:

> Hemoglobin decreased compared with the previous measurement.

But the agent must cite the returned source IDs.

# 37. Contradiction Investigation Pattern

The contradiction agent should follow:

```text
1. Receive candidate contradiction
        ↓
2. Identify required source records
        ↓
3. Retrieve original records
        ↓
4. Compare timestamps
        ↓
5. Compare claims
        ↓
6. Check documentation context
        ↓
7. Determine classification
        ↓
8. Produce evidence-backed finding
```

Possible outcomes:

```text
VERIFIED_CONTRADICTION
DOCUMENTATION_DELAY
AMBIGUOUS
FALSE_POSITIVE
INSUFFICIENT_EVIDENCE
```

---

# 38. Example CASE-001 Investigation

The timeline agent may discover:

```text
EVT-006
occurred_at = January 18
```

The contradiction agent then retrieves:

```text
DOC-009
```

and discovers:

```text
Note states event began January 24.
```

The agent must not immediately conclude:

```text
Contradiction!
```

It should retrieve supporting context.

For example:

```text
get_clinical_note(DOC-009)
get_lab_results(...)
get_encounters(...)
```

Then verification determines whether the discrepancy is genuine.

# 39. Evidence Citation Format

Agent findings should cite sources explicitly.

Example:

```json
{
  "claim": "The documented onset date conflicts with an earlier record.",
  "source_refs": [
    {
      "type": "clinical_event",
      "id": "EVT-006"
    },
    {
      "type": "document",
      "id": "DOC-009"
    }
  ]
}
```

No source IDs means the finding cannot become verified evidence.

# 42. Tool Description Rules

Tool descriptions are part of the agent's operating environment.

Descriptions must tell the model:

1. What the tool does
2. When to use it
3. What it returns
4. What it does not determine

Example:

```text

time range. Returns structured values, units, timestamps, status,
and source references. This tool retrieves laboratory evidence;
it does not determine clinical significance.
```

Descriptions must be concise and precise.

# 59. Final Architectural Rule

The tool layer is not a convenience API.

It is the boundary that turns CASETRACE from:

> **an LLM pretending to investigate a patient**

into:

> **an AI investigator operating inside a controlled clinical information environment.**

Therefore:

**Agents reason.**

**Tools retrieve.**

**Services access clinical systems.**

**Repositories access storage.**

**Verification validates claims.**

**Evidence proves findings.**

No layer should silently take over another layer's responsibility.

## Generalization audit observability

The existing tool audit emits an additional `tool.page` event after a successful
result, carrying tool_execution_id, record_count, total, has_more and source
representation kinds. It carries no note text or raw search string. Existing
tool.completed source references and sanitized tool-audit arguments remain.
Finding proposals also record source_refs, rule and candidate_type, without
claim text. These are observable evidence handoffs, not private reasoning.
